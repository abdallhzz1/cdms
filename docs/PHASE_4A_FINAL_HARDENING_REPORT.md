# Phase 4A Final Hardening Report

## Overview
This document serves as the final integration and hardening audit of Phase 4A (Manual Clinical Assignment Foundation). It outlines the vulnerabilities discovered during the audit, the performance bottlenecks identified, and the specific hardening steps taken to prepare the module for production.

---

## 1. Problems Discovered & Root Causes

### Problem 1: `validateState` N+1 Query Bottleneck
**Root Cause**: The initial implementation loaded the student relationship mapping for every assignment individually within a `foreach` loop (`Student::with(...)->find($studentId)`). When validating numerous manual assignments during a single HTTP request (e.g., mass updates or large version saves), this would trigger N+1 database queries.

### Problem 2: Subgroup Identity Spoofing
**Root Cause**: The system was resilient to subgroup tampering at the algorithm level because it generated its own "pseudo-subgroups" based on authoritative backend records. However, it did not explicitly reject an invalid `student_subgroup_id` passed in the HTTP payload, nor did it return a structured 422 if a student had no valid subgroup. It merely threw a generic backend `GROUP_NOT_FOUND` exception.

### Problem 3: Weak Route-Level Version Ownership
**Root Cause**: In the `PUT` and `DELETE` endpoints, cross-version manipulation (updating an assignment belonging to Version A through the URL of Version B) was intercepted deeply within the Service layer via a generic `Exception`. It was not rejected at the routing/HTTP layer, violating REST API best practices and missing an opportunity for early rejection.

---

## 2. Exact Fixes Implemented

### Fix 1: O(1) Query Optimization
The `DistributionManualAssignmentService::validateState()` method was entirely rewritten. 
- It now extracts all unique `student_id`s from the payload.
- Executes exactly **one** database query: `Student::with(['groupAssignments'...])->whereIn('id', $studentIds)->get()`.
- Iterates over the pre-loaded dictionary in memory to construct the pseudo-subgroups.

### Fix 2: Authoritative Subgroup Verification
Added explicit integrity checks inside `validateState()`. 
- If the student lacks a group assignment for the rotation's academic year, it immediately throws an HTTP 422 `student_subgroup_id` validation error.
- If the client supplies a `student_subgroup_id` that does not match the authoritative backend record for that student, it immediately throws an HTTP 422 validation error.

### Fix 3: Scoped Route Bindings
Modified `routes/api.php` to chain `->scopeBindings()` to the `PUT` and `DELETE` manual assignment endpoints. 
- Laravel now automatically validates that the `StudentClinicalAssignment` path parameter belongs to the `DistributionVersion` path parameter.
- Cross-version attempts now securely return a standardized HTTP `404 Not Found`.
- To support this, added the `assignments()` relationship to the `DistributionVersion` model.

---

## 3. Security Implications

These changes drastically reduce the attack surface of the manual assignment module.
1. **RBAC Reinforcement**: Administrative users cannot accidentally (or maliciously) overwrite assignments from one Distribution Version into another.
2. **Data Integrity**: The system guarantees that every manual assignment rigorously respects the academic year, rotation, and subgroup constraints established by the clinical administration. A student cannot be manually "forced" into a block using a phantom subgroup.
3. **Denial of Service (DoS)**: The elimination of N+1 queries guarantees that a malicious user cannot exhaust database connection pools by submitting a payload containing hundreds of manual assignment validations.

---

## 4. Performance Measurements

A dedicated, scalable regression test (`test_manual_assignment_performance_does_not_exhibit_n_plus_one`) was added and executed.

The test measured database queries generated by the endpoint when a new assignment was added to an existing pool of `X` assignments:
- **X = 1**: 6 queries
- **X = 5**: 6 queries
- **X = 20**: 6 queries

**Conclusion**: Query scaling is O(1) relative to the number of existing assignments in the version. The N+1 vulnerability has been completely eradicated.
