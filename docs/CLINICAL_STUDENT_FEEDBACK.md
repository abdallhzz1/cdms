# Clinical student assessments and confidential feedback

Student link: `/portal/clinical-assessments`. Staff workspace: `/clinical-student-feedback`.

## Enabling a course

The clinical director initially has configuration, publication, summary, comment and moderation permissions. Dean/Vice Dean have summary and redacted-comment access. Quality has summary, redacted-comment and moderation access. Technical administrators receive no automatic feedback access. The administrator can change these grants under **Clinical Student Feedback** in the permission matrix, including individual permissions through the existing user tools. Permission revocation is enforced on every API request.

1. Open the staff workspace, select **Clinical period → Cohort → Course** in the separate dependent selectors, then **Access and publication**. The period label includes the academic year; courses and cohorts from other periods are excluded.
2. Enable that rotation from the desired assessment week. Every rotation starts disabled; the migration enables none. Previously configured rotations remain in the staff selector for historical review even after unpublication.
3. Publish a selected week range (the remaining full rotation is selected initially). Publication records standing authorization for those weeks, including weeks with no grade yet. An owned week is shown as **Not yet assessed by the supervisor** while its official assessment is missing, draft or returned. Once a valid submitted/approved assessment exists and the week has ended, feedback becomes available automatically. Period-based courses use the period ending in that range. Mini-OSCE and final OSCE are outside this release channel.
4. Share the student link. No QR, new student account, or password is required.
5. Authorized reviewers see responses immediately, starting with the first reply; no report release action or period-end wait is required. The active results/comments tab refreshes every five seconds while visible. Original comments require moderation permission; comment readers still receive only explicitly redacted copies.

## Student flow

The portal always verifies an emailed one-time code independently of `GROUP_REGISTRATION_OTP_ENABLED` and the schedule portal. Changing that test setting cannot bypass grade authentication. Only active, academically registered clinical students are eligible. An unknown/ineligible number receives the same response shape. Codes expire after ten minutes and five failed attempts; successful codes cannot be replayed. Mail failure consumes the challenge and logs only the exception class. The configured student university email domain is reused.

The grade cookie is encrypted independently of Sanctum, HttpOnly, SameSite=Lax, secure in production, and restricted to the student API path. The normal cookie is browser-session scoped with an eight-hour server expiry. Optional remembering lasts thirty days. Sign-out revokes it on the server; changing eligibility also prevents access. Public requests enforce exact same-origin and a non-simple custom header on mutations, independently of Sanctum's domain configuration. No grade/session tokens appear in URLs or local storage.

A student sees only their own current published course assignments within staff-published weeks. They choose **Clinical period → Week / period** in two selectors, with no course selection. Changing the period resets the week. Assessments sharing the same week/range and dates appear together; if more than one course applies, each assessment has a small course heading and its own feedback/mark gate. Identically numbered weeks with different dates remain distinct and show their start dates for clarity. Choices remain stable during background refreshes. The portal checks for newly available assessments every thirty seconds while active and provides a refresh button for pending weeks. Pending weeks have no feedback form. Two short ratings become required only after a valid official assessment is ready; each can explicitly be “Unable to assess” (stored as null, never as zero rating). Free text is optional. Replies are immutable and are not retrieved by student endpoints.

The server omits the mark entirely until participation, week authorization, official assessment readiness and the week-end gate are all satisfied. It never sends the internal supervisor notes, criteria, other students or assessment records. In newly published week ranges, later official grades and corrections are available automatically; draft, returned, invalid, future and superseded assessments cannot disclose marks or accept new feedback. A submitted/approved replacement restores visibility without another reply for an already completed logical slot. Existing pre-update snapshot releases retain their strict matching/republication rules until staff publish the week range under the new behavior. Weekly keys survive distribution version changes within a rotation. All student and staff feedback responses are private/no-store.

## Confidentiality and reporting

Participation is a separate student/rotation/slot/day ledger. Answers have random UUIDs, slot and assigned-supervisor context, two ratings and encrypted free text. They contain no student ID/number, grade ID, participation ID, respondent hash, device, IP or precise timestamp; no key connects the two records. Student participation is not added to the staff audit feed. This is application-level separation and controlled disclosure, not a claim of cryptographic anonymity against database administrators, backups, database transaction logs or self-identifying writing. Privileged infrastructure access remains governed by the institution's security policy.

At the owner's explicit request, reporting is live from the first response, aggregated by course window, logical assessment slot and supervisor. Each numeric average uses all available numerical ratings for that question; “Unable to assess” values remain null, are excluded from the denominator, and never count as zero. A wholly unrated question displays a dash. Subsequent responses update the same summary rather than creating one card per response. Legacy batched and previously waiting answers are both included, without backfill or duplicate counting. There are no participant-name lists, exact reply times, per-student drill-downs, exports or delete endpoints. Immediate small-count reporting permits timing/group-context inferences that the earlier five-person frozen batches reduced; the UI must not promise threshold-based anonymity.

Reviewers cannot access results/comments about their own linked person, even if they hold multiple administrative roles. Course/department and RTA cohort scope also apply. Moderators can read originals immediately, remove identifying details, and explicitly save a redacted copy for comment readers. Empty redacted copies stay hidden. Concurrent moderation is protected by a version fingerprint so stale edits cannot overwrite a newer redaction. Originals remain encrypted; audit entries record the action and status, never comment contents. Text renders as plain React text, never HTML. Urgent concerns use the department's separate direct channel.

Published mark/participation history prevents directory force deletion of that student; schedule deletion also refuses to erase feedback history even when no mark has been entered. Empty configuration windows cascade with an otherwise deletable schedule; changing their status is supported. Ephemeral authentication records cascade on deletion of an otherwise deletable student. Disabling a window hides its student portal records without rewriting academic data or feedback. Historical records remain retained; rollback of the migration is deliberately blocked to avoid dropping confidential academic evidence.

## Operations and validation

Run the additive migrations before deploying the compiled frontend. `2026_11_26_170000_add_clinical_week_publications` adds a unique window/week authorization ledger with publisher and publication time. It does not backfill old publication decisions: **publish the desired range once after updating** to enable automatic later-grade availability for that range. Repeating publication is idempotent. Disabled windows and configured start weeks remain enforced; authorization cannot exceed rotation duration. There is no grading formula, existing supervisor dashboard or assessment-entry workflow change. Existing SMTP delivery and HTTPS must be working. The student page uses one column, touch-sized controls and 16px inputs to prevent iOS focus zoom; Arabic/English and narrow phone/tablet/desktop layouts are checked with synthetic data.

`clinical-portal:prune` removes challenges expired for two days and sessions expired/revoked for thirty days. It is scheduled daily at 03:45 through the existing Laravel scheduler; academic records and feedback are retained. Limits distinguish challenge/student-cookie buckets and permit a shared classroom network, while code verification also has a database attempt limit.

Live reporting requires no new migration or release/backfill command. Legacy batch records remain retained for history and deletion protection; the old release endpoint is an authorized, scoped compatibility no-op returning `automatic: true`.

Feature tests cover authentication, real encrypted cookie round trips without Sanctum domain assumptions, revocation/expiry, shared-network limits, cross-student keys, CSRF origin/port restrictions, duplicate requests, grade gating, corrections, historical/future marks, bulk publication query growth, period-based marks, encrypted identity-free answer schema, immediate single responses during an ongoing period, stable live summaries, null rating denominators, legacy/waiting answers, self-review denial, scope, raw/redacted permissions, safe deletion and credential cleanup. UI tests cover required short answers, optional text/remembering, retries preserving answers, keeping the selected week after submission, single-response display and polling, removal of batch controls, and restricted reviewer controls. These are local automated and synthetic browser checks, not a claim of a production penetration test or a production load benchmark.
