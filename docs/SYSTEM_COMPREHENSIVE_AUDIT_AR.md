# تقرير المراجعة الشاملة لنظام إدارة الدائرة السريرية (CDMS)

**تاريخ المراجعة:** 24 آب 2026  
**نطاق المراجعة:** المستودع الحالي كاملًا (Backend، Frontend، قاعدة البيانات، الاختبارات، التوثيق، التشغيل والأمان)  
**نوع المراجعة:** مراجعة ساكنة للكود والوثائق مع تشغيل الفحوصات المتاحة محليًا

## 1. الملخص التنفيذي

النظام لم يعد مشروع تأسيس أو نموذجًا أوليًا بسيطًا؛ الكود الحالي يمثل منصة واسعة لإدارة العمل الأكاديمي والسريري، تضم **247 تعريف مسار API، و70 migration، و57 Model، و52 Controller، و25 Service، و68 صفحة React**. تم تنفيذ معظم الوحدات الأساسية المخطط لها: إدارة الطلبة والموظفين، الخطط والمساقات، التوزيع السريري، الحضور والتقييم والدرجات، الإرشاد، الجودة، المراسلات والاجتماعات، التقارير، وإدارة النظام.

التقييم العام الحالي: **النظام متقدم وظيفيًا وقريب من مرحلة اختبار قبول وتشغيل تجريبي، لكنه غير جاهز لإعلان إنتاج نهائي قبل إغلاق فجوات الصلاحيات، تحديث التوثيق، وإعادة تنفيذ بوابة الاختبارات كاملة في بيئة PHP/MySQL صالحة.**

أقوى جوانب المشروع هي اتساع التغطية الوظيفية، فصل React عن Laravel، وجود نموذج صلاحيات ومراحل عمل، دعم العربية والإنجليزية، ووجود تاريخ كبير من اختبارات وتقارير المراحل. أهم المخاطر الحالية هي تفاوت تطبيق الصلاحيات الدقيقة بين المسارات، غياب Policies مستقلة، تضخم ملف routes، وجود مسارات تشغيلية عامة أو شبه عامة تحتاج مراجعة خصوصية، واعتماد بعض تقارير النجاح السابقة على اختبارات لم يُعد تشغيلها في هذه المراجعة.

## 2. ماذا أنجز النظام؟

### أ. الأساس التقني

- واجهة React 19 + TypeScript + Vite، مع React Router وTanStack Query وReact Hook Form وZod.
- Backend مبني على Laravel 12 وPHP 8.3، وREST API بإصدار `/api/v1`.
- مصادقة جلسات عبر Laravel Sanctum، وليست Bearer Tokens.
- قاعدة بيانات MySQL مصممة عبر migrations، مع جلسات وCache وJobs وإشعارات وسجل تدقيق.
- صيغة موحدة لاستجابات API، ودعم مركزي للاتصال ومعالجة الأخطاء في الواجهة.
- دعم عربي/إنجليزي واتجاه RTL/LTR، مع سياق i18n واختبارات أساسية له.

### ب. المستخدمون والصلاحيات والإدارة

- تسجيل الدخول والخروج وجلب المستخدم الحالي.
- أدوار وصلاحيات وربط المستخدمين بالأدوار ونطاقات الوصول.
- إدارة المستخدمين، تفعيل/تعطيل الحساب، إعادة كلمة المرور، وتعيين الأدوار.
- شاشة مصفوفة الصلاحيات، الجلسات النشطة، صحة النظام، الإعدادات، وسجل التدقيق.
- إدارة الأقسام وتعيين رؤساء الأقسام ومساعدي البحث والتدريس.

### ج. البيانات الأكاديمية والأشخاص

- السنوات الأكاديمية، الأقسام، مواقع التدريب والشراكات.
- الطلبة ومجموعاتهم ومجموعاتهم الفرعية والاستيراد الجماعي وتعيين المرشدين.
- الموظفون، رؤساء الأقسام، المشرفون السريريّون وملفاتهم ووثائقهم وتقييماتهم.
- المساقات والخطط الدراسية وربط المساقات بالخطط ومخرجات البرنامج.
- تسجيل الطلبة في المساقات، الدرجات والإدخال الجماعي والاعتماد والإرجاع.

### د. التدريب والتوزيع السريري

- الدورات والكتل السريرية والسعة والتوفر ومواقع التدريب.
- إنشاء نسخ التوزيع، التوليد المقترح، التعديل اليدوي، فحص التعارضات وغير الموزعين.
- اعتماد ونشر ومقارنة نسخ التوزيع والاحتفاظ بالنسخة الحالية.
- الجداول التشغيلية للطلبة والمشرفين والأقسام ومواقع التدريب.

### هـ. العمليات الأكاديمية والإدارية

## 4. نتائج الفحص المنفذ

| الفحص | النتيجة | الملاحظة |
|---|---|---|
| TypeScript (`npm run typecheck`) | ناجح | لا توجد أخطاء TypeScript في الفحص الحالي |
| ESLint (`npm run lint`) | لم يبدأ | أمر lint موجود، لكن حزمة `eslint` غير موجودة في devDependencies/التثبيت |
| Vitest | تعذّر في بيئة المراجعة | أداة البناء حاولت قراءة مسار خارج مساحة العمل المسموح بها؛ لا يُعد هذا وحده فشلًا وظيفيًا |

| Laravel/PHPUnit | لم يبدأ | executable الخاص بـ PHP غير متاح في بيئة المراجعة الحالية |
| حالة Git | نظيفة قبل إنشاء التقرير | لم تكن هناك تعديلات مستخدم غير محفوظة عند بدء المراجعة |

تقرير المرحلة 7A-R الموجود في المشروع يسجل تاريخيًا نجاح **264/264 اختبار Backend و34/34 اختبار Frontend**، لكن لا ينبغي اعتبار ذلك شهادة للحالة الحالية دون إعادة التشغيل بعد التغييرات اللاحقة؛ سجل Git يبين وجود تغييرات وظيفية بعد ذلك التقرير.

## 5. المشاكل والمخاطر

### أولوية حرجة — يجب إغلاقها قبل الإنتاج

#### 1. عدم اتساق حماية مسارات API بالصلاحيات الدقيقة

كل المسارات التجارية تقريبًا داخل `auth:sanctum`، وهذا جيد كبداية، لكن توجد مجموعات من المسارات لا يظهر عليها middleware لصلاحية محددة، ومنها مسارات رؤساء الأقسام والمشرفين، بعض أعباء المشرفين، lookup للمستخدمين، الجدول التشغيلي، وحفظ/قراءة `operational/distribution-payload`. الاعتماد على تسجيل الدخول فقط قد يسمح لمستخدم داخلي بالوصول إلى بيانات أو عمليات خارج دوره إذا لم ينفذ Controller تحققًا داخليًا مكافئًا.

**المطلوب:** إعداد مصفوفة route-to-permission آلية، ثم إلزام كل endpoint بصلاحية ونطاق، واختبار 403 لكل دور غير مصرح له. يجب إعطاء أولوية خاصة لمسارات الرفع والحذف والتقييم والتعديل وpayloads التشغيلية.

#### 2. مسار الجدول السريري العام يحتاج مراجعة خصوصية

`/api/v1/public/clinical-schedule` متاح دون مصادقة ومخصص لشاشات العرض/البحث. طبيعة البيانات المعادة يجب تدقيقها للتأكد من عدم كشف أسماء طلبة أو مشرفين أو تفاصيل شخصية أكثر من الحاجة، مع rate limit وتقليل الحقول ومنع enumeration.

**المطلوب:** تعريف واضح للبيانات العامة المسموحة، استخدام DTO/Resource مخصص، إضافة rate limiting، واختبارات تمنع تسرب identifiers والحقول الحساسة.

#### 3. لا توجد Laravel Policies مستقلة رغم أن المعمارية تعتمد Policy/Gate/Scope

العداد الحالي لملفات `app/Policies` هو صفر. يوجد middleware وخدمة Authorization ونطاقات، لكن غياب Policies يجعل قواعد الوصول أكثر عرضة للتشتت بين routes وControllers/Services، ويصعّب تدقيق الوصول على مستوى السجل.

**المطلوب:** نقل صلاحيات السجل الحساسة تدريجيًا إلى Policies أو طبقة Authorization مركزية موثقة، خصوصًا الطلبة، الإرشاد، الدرجات، التوزيع، ملفات الموظفين والمرفقات.

#### 4. لا توجد شهادة اختبار حديثة قابلة لإعادة الإنتاج في هذه المراجعة

الاختبارات السابقة ممتازة كمؤشر، لكن بوابة الإصدار الحالية غير مثبتة لأن PHP/MySQL لم يكونا متاحين هنا، بينما Vitest/build اصطدما بقيد البيئة. لا يجوز ترقية نسخة إنتاجية اعتمادًا على تقرير تاريخي فقط.

**المطلوب:** CI نظيف يشغل `composer install`، migrations على قاعدة اختبار، كامل PHPUnit، typecheck، lint، Vitest، وبناء production في كل push/PR.

### أولوية عالية

#### 5. README وARCHITECTURE متأخران جدًا عن الواقع

كلاهما يذكر أن المشروع عند Phase 2 ولا توجد وحدات أعمال، بينما المستودع يحتوي معظم النظام وتقارير حتى Phase 7C. هذا يسبب إعدادًا خاطئًا، قرارات خاطئة للمطورين، وصعوبة في التسليم والصيانة.

**المطلوب:** تحديث الحالة، الوحدات، قائمة endpoints، أوامر التشغيل، بيانات demo، وحدود ما اكتمل وما يزال تجريبيًا.

#### 6. ملف routes/api.php متضخم ومتكرر

الملف يجمع مئات المسارات ووحدات مختلفة، ويتضمن تعريفات متقاربة أو مكررة لإدارة المستخدمين تحت `/admin` وبشكل مباشر. كما يحتوي route closure يستعلم من قاعدة البيانات داخل ملف المسارات. هذا يزيد مخاطر تعارض الأسماء، اختلاف الحماية، وصعوبة route caching والصيانة.

**المطلوب:** تقسيم المسارات حسب module، نقل closure إلى Controller، إزالة التكرار، وتشغيل `php artisan route:list` و`route:cache` كجزء من CI.

#### 7. أداة lint معلنة لكنها غير مجهزة

`package.json` يحتوي `eslint .` لكن ESLint غير موجود في devDependencies. لذلك بوابة جودة أساسية معطلة.

**المطلوب:** إضافة ESLint والحزم/config المتوافقة مع React 19 وTypeScript، تثبيت lockfile، ثم إصلاح كل النتائج وربطها بـCI.

#### 8. تغطية Frontend محدودة مقابل حجم الواجهة

يوجد 68 صفحة React مقابل 8 ملفات اختبار مرصودة. حتى لو احتوت بعض الملفات على حالات كثيرة، ما تزال وحدات حساسة مثل الدرجات والتوزيع والمراسلات والجودة والإدارة بحاجة إلى اختبارات مسارات وصلاحيات ونماذج وحالات الخطأ.

**المطلوب:** التركيز على اختبارات السلوك عالية الخطورة، وليس snapshot فقط: الصلاحيات، الحفظ الجماعي، الاعتماد/النشر، RTL، أخطاء الشبكة، والتعارضات.

#### 9. أمان السجل Scope غير مكتمل حسب وثائق المشروع نفسها

تقرير 7A-R يذكر أن `AuthorizationService` كان يقبل فعليًا `scope_type=global` وأن النطاقات الديناميكية المعقدة لم تكن مكتملة حينها. توجد commits لاحقة لإضافة department scoping، لكن يلزم تدقيق شامل لبقية الأنواع: own/advisor/supervisor/department/college.

**المطلوب:** اختبارات عزل بيانات متعددة المستخدمين لكل Scope، تشمل محاولة الوصول المباشر إلى IDs خارج النطاق.

### أولوية متوسطة

#### 10. وجود عدد كبير من سكربتات الإصلاح والملفات المؤقتة في المستودع

توجد ملفات `fix_*.py` و`scratch_*.php` وملفات extracted/raw في مجلدات التطبيق. هذه ليست بالضرورة ثغرة، لكنها ترفع ضوضاء المستودع وقد تتضمن عمليات صيانة غير مضبوطة أو تُستخدم بالخطأ.

**المطلوب:** تصنيف ما يلزم الاحتفاظ به ونقله إلى `tools/` مع README، وحذف/أرشفة الباقي بعد مراجعة واعتماد، وإضافة قواعد `.gitignore` مناسبة.

#### 11. احتمال عدم اكتمال اتساق طبقات المعمارية

المعمارية تنص على Controllers → Services → Domain/Policies، لكن وجود 52 Controller مقابل 25 Service و0 Policies يرجح أن بعض منطق الأعمال أو التفويض بقي داخل Controllers. ظهر مثال واضح لرمي Exception خاص بقيد الدرجة داخل `GradeEntryController`.

**المطلوب:** تدقيق Controllers الكبيرة ونقل قواعد الأعمال والمعاملات إلى Services/Domain، مع Exceptions نوعية ورسائل API موحدة.

#### 12. معالجة الاستثناءات تحتاج توحيدًا

بعض الخدمات ترمي `Exception` عامة، مثل التحقق النهائي للتوزيع أو عدم انتماء assignment للنسخة. الاستثناء العام يصعب تحويله إلى HTTP status ورسالة آمنة ومتوقعة.

**المطلوب:** Domain Exceptions محددة، ربطها مركزيًا بـ409/422/403/404، ومنع تمرير تفاصيل داخلية للمستخدم.

#### 13. التوثيق التشغيلي جيد لكنه يحتاج تحققًا حيًا

دليل الإنتاج يغطي HTTPS وCookies وCORS والQueue والنسخ الاحتياطي، لكنه وثيقة لا تثبت أن البيئة الفعلية مطابقة. كما أن خطوات restore وRTO/RPO تحتاج تمرينًا موثقًا، لا مجرد إجراء مكتوب.

**المطلوب:** staging مطابق للإنتاج، restore drill دوري، فحص queue/scheduler، ومراقبة failed jobs ومساحة التخزين وانتهاء النسخ الاحتياطية.

## 7. خطة الإصلاح المقترحة

### خلال 1–3 أيام: بوابة الأمان والبناء

1. تجهيز CI وتشغيل كامل الاختبارات والبناء في بيئة غير مقيدة.
2. إصلاح إعداد ESLint وإضافته إلى الاعتماديات.
3. استخراج قائمة route middleware آليًا وتحديد كل endpoint بلا permission دقيقة.
4. حماية payload والـlookup والرفع والحذف والتقييم والمسارات التشغيلية.
5. تدقيق response لمسار الجدول العام وإضافة rate limit.

### خلال أسبوع: الصلاحيات والصيانة

1. اختبارات Role × Permission × Scope، مع عزل record-level access.
2. تقسيم `routes/api.php` حسب الوحدات وإزالة التكرار والـclosure.
3. إنشاء Policies/Authorization rules للوحدات الحساسة.
4. نقل business rules الباقية من Controllers إلى Services.
5. تنظيف scripts وملفات artifacts المؤقتة.

### خلال أسبوعين: اعتماد ما قبل الإنتاج

1. تحديث README وARCHITECTURE وخريطة الوظائف الفعلية.
2. توسيع اختبارات Frontend للمسارات الحرجة والأدوار وRTL.
3. UAT يدوي لكل دور باستخدام بيانات demo الواردة في Phase 7C.
4. اختبار migrations من قاعدة فارغة ومن نسخة سابقة، واختبار rollback المخطط.
5. اختبار backup/restore فعلي، Queue، Scheduler، البريد، التخزين والصلاحيات.
6. فحص أمني نهائي: CSRF/CORS/Cookies، رفع الملفات، IDOR، rate limits، وتسرّب البيانات.

## 8. معايير واضحة لإعلان الجاهزية للإنتاج

لا يُنصح بإعلان النظام جاهزًا للإنتاج إلا بعد تحقق جميع البنود التالية:

- نجاح 100% لاختبارات Backend وFrontend وtypecheck وlint وproduction build في CI.
- عدم وجود endpoint تجاري بلا permission معلنة ومختبرة، إلا public endpoints المعتمدة رسميًا.
- نجاح اختبارات Scope وعزل السجلات لكل دور.
- نجاح مراجعة الخصوصية للجدول العام والتصدير والمرفقات.
- تنفيذ UAT وتوقيعه من ممثلي الدائرة لكل workflow حرج.
- نجاح restore drill ضمن RTO/RPO المعلنين.
- تحديث التوثيق بحيث يطابق النسخة المنشورة.
- وجود خطة rollback ومراقبة وسجل تغييرات للإصدار.

- إنشاء trait مركزية `HasSafePagination` تضمن أن `per_page` موجب ومقيد بحد أعلى معروف بدل قبول أرقام غير محدودة من العميل.
- تطبيق الحدود على المستخدمين والمساقات والعلامات وسجل التدقيق والاستبيانات، مع إبقاء حدود أعلى متوافقة مع احتياجات الشاشات الحالية.
- تحويل تصدير Audit Logs من `get()` الذي يحمل كامل السجل في الذاكرة إلى `lazyByIdDesc` بحزم 500 سجل أثناء streaming.
- نقل تلخيص إجابات الاستبيان من تحميل جميع الإجابات وتجميعها في PHP إلى `COUNT` و`AVG` و`GROUP BY` داخل قاعدة البيانات.
- جعل قائمة إجابات الاستبيان paginated بحد أقصى 100، مع بقاء الملخص محسوبًا على كامل البيانات وليس الصفحة الحالية فقط.
- إزالة N+1 في مرشحي رؤساء الأقسام ومساعدي البحث والتدريس عبر eager loading لعلاقة `person` بدل استعلام منفصل لكل مستخدم.
- تحميل قسم الملف الشخصي مسبقًا في قوائم وعرض رؤساء الأقسام والمشرفين لتجنب lazy queries داخل mapping.
- إزالة `firstOrCreate` من endpoints القراءة لملفات رؤساء الأقسام والمشرفين؛ GET لم يعد ينشئ ملفًا لكل مستخدم مفقود.
- إزالة الحذف وإعادة الإنشاء التلقائي لملف المشرف أثناء GET عند وجود ترميز قديم؛ تعرض قيمة fallback مؤقتة دون تغيير البيانات.
- إضافة اختبار يثبت تقييد `per_page=10000`، واختبار يثبت أن طلب القائمة والعرض الفردي لا ينشئ ملفات شخصية.

نجح فحص TypeScript و`git diff --check`. يلزم تشغيل PHPUnit وقياس query counts وذاكرة التصدير على بيانات مماثلة للإنتاج عند توفر PHP وقاعدة اختبار.

## 20. تحديث المعالجة — الدفعة العاشرة: الجاهزية التشغيلية والتعافي (24 آب 2026)

تمت مطابقة التوثيق التشغيلي مع التنفيذ الفعلي ومعالجة الفجوات التالية:

- توسيع `/api/v1/health` ليعرض حالة التطبيق وقاعدة البيانات والـQueue والتخزين وعدد failed jobs بدل فحص قاعدة البيانات فقط.
- كشف jobs غير المحجوزة التي تجاوزت مهلة قابلة للضبط كحالة `stalled` وإرجاع HTTP 503.
- فحص قابلية الكتابة ومساحة التخزين الحرة بحد أدنى قابل للضبط، دون كشف المسار أو تفاصيل الاستثناء في الاستجابة العامة.
- إضافة `failed_jobs_count` مع قيمة `-1` عند تعذر القراءة، وتسجيل السبب داخليًا فقط.
- إنشاء `config/operations.php` بدل استخدام `env()` مباشرة في كود التشغيل، ليبقى السلوك صحيحًا مع `config:cache`.
- إضافة أمر `php artisan cdms:readiness` يفشل بـexit code غير صفري عند نقص APP_KEY، إعدادات الإنتاج الآمنة، Queue worker، Session، CORS، النسخ الاحتياطي، S3 أو تشفير الأرشيف.
- جدولة تنظيف failed jobs الأقدم من 30 يومًا يوميًا.
- تجهيز جدولة `backup:run --only-db` و`backup:clean` و`backup:monitor` مع `withoutOverlapping` و`onOneServer`، لكن فقط عندما يكون النسخ مفعّلًا والحزمة موجودة فعليًا.
- إضافة تعريف S3 الخاص في `filesystems.php` ومتغيرات البيئة اللازمة، مع `private visibility` وthrow/report للأخطاء.
- تحديث الاختبارات القديمة حتى لا تعتبر config غير قابل للتنفيذ نسخة احتياطية حقيقية، وإضافة اختبار لفشل readiness عند تعطيل backup واختبار جدولة تنظيف failed jobs.
- إضافة تحذير صريح إلى دليل التشغيل بأن `composer.lock` الحالي لا يحتوي حزمة Spatie أو S3 adapter.

**مانع إنتاج قائم:** النسخ الاحتياطي غير منفذ فعليًا بعد؛ `spatie/laravel-backup` وS3 Flysystem adapter غير موجودين في `composer.json/lock`. يجب تثبيتهما في بيئة تحتوي PHP/Composer، تحديث lock، ضبط S3 وكلمة تشفير الأرشيف، تفعيل `BACKUP_ENABLED=true`، ثم تنفيذ backup يدوي واختبار restore كامل قبل اعتماد RPO/RTO. نجح فحص TypeScript و`git diff --check` في البيئة الحالية.
